# Движок игры как среда обучения

Задача: учить политику v3.1 не на Python-симуляторе (`tools/rl/sim_env.py`, своя упрощённая модель мира), а на самом
движке Minecraft 1.7.10, тем же протоколом среды (контракт 3.1, [`CONTRACT-v2.md`](CONTRACT-v2.md)). Здесь — где
уходит время тика в нынешней среде, как устроен прототип «N арен в одной JVM», что в нём ускорено и меняет ли это игру,
замеры, проверка эквивалентности и короткое обучение. Всё ниже измерено на этом ПК (i7-10700K, 8 ядер / 16 потоков,
48 ГБ), если не сказано иное.

## 1. Профиль: куда уходит тик

Выделенный сервер со средой (`-Daiguide.rl=<порт> -Daiguide.rl.fast=true -Daiguide.rl.contract=3.1`), один агент,
политика `v31-sim-epoch-472` (выбор по распределению), 150 с записи Java Flight Recorder (Oracle 8u401, `settings=profile`,
глубина стека 512) на каждый сценарий. Файлы старого формата 0.9 читает парсер JMC (`tools/rl/engine/JfrDump.java`),
разбор по видам работы — `tools/rl/engine_prof.py` (сэмпл относится к первому подходящему виду: поиск пути раньше
вызвавшего его кода мода, свет раньше изменения блока). Доли — от сэмплов серверного потока (около 10 тыс. на сценарий),
то есть от его процессорного времени; ожидание политики в них не входит.

Сквозь виды: 27–35 % всех сэмплов — `LongHashMap.getValueByKey/getEntry` наверху стека (поиск загруженного чанка при
каждом `World.getBlock`, `chunkExists`), 5–15 % — `IntHashMap` поиска пути (карта точек с `HashSet<Integer>` ключей).

Выводы:

- **Поиск пути — главный расход** (wood 54 %, pickaxe 62 %, iron 23 %, волны 69 %). Это игровая логика: проба
  `MindSkills.reachableTrunks` (факт маски `trees_free` и признак `trees_reachable` — до 5 поисков на решение, с
  кэшем 10 с), `Body.walkTo` агентов и ИИ мобов. Убрать нельзя, можно сделать тот же поиск быстрее (раздел 3).
- **Внутри него и вообще везде — хеш чанков.** `LongHashMap` игры хеширует ключ чанка как `x ^ z`: чанки квадрата
  вокруг спауна (арена 11×11, спаун-чанки 25×25) ложатся в немногие корзины вдоль диагоналей, и каждый `getBlock`
  идёт по цепочке. Ванильный `PathFinder.canEntityStandAt` к тому же читает блоки через `entity.worldObj`, а не через
  свой `ChunkCache`.
- **Сохранение, сеть Minecraft, свет, чанки, Незер/Энд — около нуля.** Сохранение уже выключено (`disableLevelSaving`
  при сбросе), клиентов нет, свет пересчитывается только при изменении блоков. Отключать там нечего.
- **Трекинг сущностей** — 0.6–1.6 %; не трогал (ниже — почему).
- **Протокол** — 0.1–0.3 % процессора сервера. Задержка шага на стороне клиента — отдельно, раздел 4.

## 2. Прототип: арены в одной JVM

`tools/rl/engine/EngineHost.java` поднимает N арен в одном процессе Java 8. Каждая арена — полноценный выделенный
сервер Forge (`ServerLaunchWrapper` → `Launch` → `FMLServerTweaker` → `MinecraftServer`) в **своём** загрузчике
классов (`URLClassLoader` над jar Forge и `libraries/`, родитель — только JDK). Поэтому ни статика Minecraft и Forge
(`MinecraftServer.getServer()`, реестры, `DimensionManager`), ни статика мода (`Crew.instance`, `AgentMind.minds`,
`Waves.cycle`, `DefenseWorld.*` — их в моде десятки) между аренами не общие. Переписывать мод под много миров в одном
загрузчике не понадобилось. Каждая арена тикает в своём серверном потоке — параллельно по ядрам.

Что пришлось обойти:

- FML ставит свой `SecurityManager`, который запрещает себя заменить; следующая арена не стартовала бы. Хост снимает
  его перед каждой ареной через `Class.getDeclaredFields0` (в Oracle 8u401 `System.security` скрыт от
  `getDeclaredField`).
- Свойство `aiguide.rl` (порт среды) общее на JVM: арены стартуют по очереди, следующая — когда порт предыдущей
  отвечает (около 10 с на арену).
- Общие для всех: рабочая папка (`server.properties`, `mods/`, `config/`), у каждой арены свой мир
  (`--universe arena-<порт>`, копия сгенерированного мира `seed 5802634`), порт Minecraft `--port 0` (никто не
  подключается). Логи Log4j — одна конфигурация без файлов (`log4j2-engine.xml`), иначе арены писали бы в один файл.
- Кодовый кэш JIT общий, а классы у каждой арены свои: `-XX:ReservedCodeCacheSize=1024M`, иначе при многих аренах JIT
  выключился бы от переполнения. Потоки Netty — `-Dio.netty.eventLoopThreads=1` (по 32 простаивающих на арену иначе).

Протокол среды не менялся: каждая арена слушает свой порт (26200, 26201, …), `RlEnv`, `RlEnv.facts`, `RlReward` —
тот же код мода. `train.py --env engine --envs N` сам поднимает хост с N аренами (`tools/rl/engine_env.py`), подключается
к ним как к серверам (`real_env.RealEnv`, по процессу-работнику на арену) и гасит в конце; `--url` — к уже запущенным.

Запуск руками:

    python tools/rl/engine_env.py start --kind engine --n 8 --opt --xmx 5824M   # 8 арен, порты 26200..26207
    python tools/rl/engine_bench.py --ports 26200,26201 --scenario wood --seconds 120
    python tools/rl/engine_env.py stop --n 8

`--kind server` — то же, но по JVM на арену (обычные выделенные серверы, для сравнения). Пока запущена League of Legends,
`engine_env` даёт не больше 2 арен и ставит Idle, иначе BelowNormal (`train.py` и бенч тоже уходят в Idle).

Подготовка (один раз): `build/rl/servers/template/` — Forge 1.7.10-10.13.4.1614, `minecraft_server.1.7.10.jar`,
`libraries/`, `config/` (как у `launch_envs.py`); `build/rl/servers/world-5802634/` — сгенерированный мир `seed 5802634`
(копия `world` любого сервера среды); моды — `python tools/build.py && python tools/build_client.py`
(`AIGUIDE_ENGINE_MODS=<папка>` — другие jar). Для профиля: jar JMC 8.3.1 (`flightrecorder`, `common`, `encoder`,
`lz4-java`) с Maven Central в `build/jmc/`.

## 3. Что ускорено и меняет ли это игру

Включается `-Daiguide.rl.engine=true` (`engine_env --opt`, по умолчанию в `train.py --env engine`; без него хост —
та же игра, что на сервере). Всё ниже **не меняет игру**: те же ответы, другая скорость.

| что | как | почему та же игра | проверка |
|---|---|---|---|
| поиск пути | `net.minecraft.pathfinding.FastPath` — `PathFinder` 1.7.10 шаг в шаг (те же точки в том же порядке, та же куча `Path`, те же правила `canEntityStandAt`, то же `getMaxFallHeight`), только блоки читаются через массив чанков вокруг старта, а точки лежат в карте с открытой адресацией вместо `IntHashMap`. Те же чанки запрашиваются у мира, что запросил бы `ChunkCache` | алгоритм и порядок те же, отличается только способ найти тот же объект | `-Daiguide.rl.engine.check=1`: каждый поиск ещё и ванильным, сравнение точка в точку. **26 993 поиска (pickaxe, waves:normal, 2 арены) и 12 311 до подмены навигаторов (pickaxe, wood, waves) — 0 расхождений** |
| кто ищет быстро | ходьба агентов (`Body.walkTo`), проба деревьев (`MindSkills.reached`), путь мобов волн к базе (`Waves.steer`) и **ИИ всех мобов и животных**: при входе живой сущности в мир её `PathNavigate` заменяется на `FastNavigate` (подкласс, состояние скопировано поле в поле; переопределены только `getPathToXYZ`, `getPathToEntityLiving`) | следование по пути, солнце, двери — код игры | то же сравнение |
| карта чанков | `ChunkProviderServer.id2ChunkMap` заменяется на `net.minecraft.util.FastLongMap` — тот же `LongHashMap` (те же ответы на `getValueByKey`, `containsItem`, `add`, `remove`, `getNumHashElements`), открытая адресация, ключ перемешан финализатором MurmurHash3. Содержимое копируется из игровой карты запись в запись | карта — та же карта | `EngineGameTest`: 200 000 смешанных операций, обход 81×81 и копия — ответы те же, что у `LongHashMap` |
| ожидание политики | серверный поток 3 мс ищет следующий запрос, прежде чем уснуть | на тики не влияет | — |

Что **не** отключал и почему:

- **Сохранение чанков** — уже выключено средой при сбросе арены; в профиле 0 %.
- **Трекинг сущностей для клиентов** (0.6–1.6 %) — `EntityTrackerEntry` сбрасывает у сущностей флаги
  (`velocityChanged`, `isAirBorne`); выгода мала, а доказать, что это не трогает логику, дороже.
- **Рассылка пакетов, сеть Minecraft** — 0 %: клиентов нет.
- **Свет** — 0–0.1 %, пересчитывается только при изменении блоков; он входит в наблюдение (`light_spots`, `safety.light`).
- **Кэш или предел дальности поиска пути мобов** («меняет игру») — не делал: точное ускорение их ИИ (`FastNavigate`)
  дало больше и игру не меняет.

## 4. Замеры

`tools/rl/engine_bench.py`: сеть `v31-sim-epoch-472` (выбор по распределению), экипаж 1, 120 с на сценарий, по
потоку клиента на среду (torch на 1 потоке), процессы — BelowNormal, League of Legends не запущена. «Решений/с» —
решения сети за секунду стены; «игр. с/с» — игровых секунд за секунду стены. ПК общий: в часть замеров рядом шёл
чужой рендер (ffmpeg, Idle), поэтому для одного ядра главное — **парный** замер (`tools/rl/engine_pair.py`: сервер и
арена движка одновременно, нагрузка вокруг одна и та же). Сервер — выделенный Forge-сервер, как сейчас для обучения
(`-Daiguide.rl.fast=true`); движок — арены в одной JVM с ускорениями раздела 3. Python-симулятор — `sim_env.SimEnv`,
та же сеть, по процессу на среду.

- **Выигрыш движка над сервером — ×1.8–2.0** и на одном ядре, и на всём ПК. Это ускорения раздела 3 (поиск пути и
  карта чанков); сам перенос в одну JVM без них скорости не даёт (A/B на двух аренах: сервер 21.4 решения/с на wood,
  движок без ускорений 20.0, с ускорениями 39.7).

  движок его не заменит по скорости, только по правдивости.
- Сброс арены: медиана 12–16 мс на одну арену, 19–31 мс на 8–14 аренах (сервер так же: 13–20 мс). Старт: около 10 с
  на арену, арены поднимаются по очереди (14 — за 2.5 мин).
- В обучении (`train.py` шагает всеми средами в ногу и ждёт самую медленную) 12 арен дали **29 решений/с** против

- Протокол (TCP на localhost) — 2–4 мс на запрос при Idle-приоритете и меньше 1 % процессора сервера. `sim_ms` в
  `info` не включает построение наблюдения (`answer()` идёт после замера), поэтому на сервере стена ≈ 2 × `sim_ms`:
  вторая половина — наблюдение и маска, а не сеть.

Сырьё: `build/rl/engine/bench-final.jsonl`, `bench-pair.jsonl`, `bench-matrix.jsonl` (Python-симулятор и сервер ×1),
`bench-ab.jsonl`, `mem-final.txt`.

## 5. Эквивалентность

Два уровня.

**Точность ускорений.** `FastPath` сверялся с ванильным поиском пути точка в точку (`-Daiguide.rl.engine.check`):
12 311 поисков до подмены навигаторов мобов (pickaxe, wood, waves:normal) и 26 993 после (pickaxe, waves:normal),
и ещё 852 выборочно (каждый 50-й) в прогоне ниже — **0 расхождений**. `FastLongMap` = `LongHashMap` на 200 000
смешанных операций (`EngineGameTest`).

**Исходы эпизодов.** Одни и те же сиды (900…914 и 1900…1914), сеть `v31-sim-epoch-472` с выбором самого вероятного действия
(`--greedy`), экипаж 1, по 30 эпизодов на сценарий: выделенные серверы (игра как есть) против арен движка с
ускорениями (`tools/rl/engine_equiv.py`, код мода один и тот же). Minecraft не детерминирован (тот же сид даёт тот же
старт, а не тот же ход), поэтому сравниваются распределения.

| сценарий | успех: сервер / движок | z | конец по времени | время до цели, игр. с (ср. ± σ) | совпало последовательностей действий |
|---|---|---|---|---|---|
| wood | 1.00 / 1.00 | 0 | 0 / 0 | 71 ± 17 / 69 ± 20 | 1 из 30 |
| pickaxe | 1.00 / 1.00 | 0 | 0 / 0 | 96 ± 86 / 99 ± 82 | 9 из 30 |
| farm | 0.83 / 0.73 | 0.94 | 5 / 8 | 487 ± 77 / 480 ± 79 | 0 |
| iron | 0.27 / 0.33 | −0.56 | 22 / 20 | 609 ± 119 / 667 ± 132 | 1 |

Разница в пределах шума (|z| < 1). Средний возврат в farm и iron не сравним: в нём редкие эпизоды с петлёй провалов
(`retry_fail` −3·10⁴ за эпизод) — то, что разбирает раздел 8. Совпадения последовательностей решений целиком (9 из 30
в pickaxe) показывают, что при одинаковом мире движок принимает те же решения.

Прогон серверной стороны шёл вечером, движковой — после ночного сна ПК (см. раздел 7); jar один и тот же
(`build/rl/engine/frozen`).

## 6. Короткое обучение на движке

`v31eng1`: от `v31-sim-epoch-472` (`build/rl/runs/v31sim4/final.pt`), 12 арен движка в одной JVM (8.2 ГБ кучи), маски
и навыки с правками раздела 8, параметры как у `v31real2` (`--lr 1e-4 --rollout 512 --minibatch 128 --ent 0.02→0.01
--credit 0.5 --reward-clip 2 --threshold 0.7 --window 30 --stage-max 25`, те же этапы wood … waves:easy), 25 минут.

| | `v31real2` (игра, 2 сервера) | `v31eng1` (движок, 12 арен) |
|---|---|---|
| время | 45.7 мин | 25.0 мин |
| эпох / решений | 74 / 37 928 | 84 / 43 501 |
| решений в секунду | 13.8 | 29.0 |
| программа | wood 2 → … → iron (по пределу, 0.03) → mine_trip (по пределу, 0.33) → farm 67 → pasture | wood 2 → pickaxe 5 → sword 9 → armor 12 → bow 17 → iron (по пределу на 42-й, 0.27) → mine_trip (по пределу на 67-й, 0.97) → farm 77 → pasture |

`train.py` шагает средами в ногу (каждый шаг ждёт самую медленную арену), поэтому 12 арен дают 29 решений/с, а не
сумму свободного бега (раздел 4).

Аудит масок под этой политикой на тех же аренах (`build/rl/engine/audit-train-v31eng1.json`, 42 635 разрешённых
решений): провалов 9.7 %, на старте 4.2 %. `place:block@below` — 49 успехов из 51 (до правок треть провалов),
`place:crafting_table` — 452 из 517. Главные оставшиеся: `ascend:surface → NO_PATH` (85 % разрешённых; агент ушёл из
своей шахты ямами и столбами, и пути к её лестнице нет), `mine:iron_ore → BLOCKED` (43 %), `descend:mine → NO_TOOL`
(24 %), `retreat:home`/`go_to:base` → `NO_PATH`.

**Проверка в обычной игре** — как в `POLICY-v3.1.md`: выделенные серверы без ускорений движка, тот же jar, что при
обучении, сид 900, экипаж 1, выбор по распределению сети, 10 эпизодов на сценарий (`play.py --url`).

| сценарий | `v31-sim-epoch-472` (мод сейчас) | `v31eng1` эпоха 84 |
|---|---|---|
| wood | 10/10 (85 игр. с) | 9/10 (88) |
| pickaxe | 10/10 (113) | 10/10 (124) |
| farm | 6/10 (785) | 9/10 (660) |
| iron | 6/10 (742) | 9/10 (479) |

`noop` в конце эпизода — 0 у обеих (у `v31real2` в iron было 3 из 3). Разница в пользу `v31eng1`, но выборка мала:

## 7. Что не получилось и что дальше

Профиль арены движка после ускорений (одна арена, JFR 100 с, `build/rl/engine/prof-engine.json`):

| что | wood | waves:normal |
|---|---|---|
| поиск пути: проба деревьев (факты среды) | 40.3 | 4.9 |

Поиск пути по-прежнему главный (wood 43 %, волны 57 %), только каждый поиск теперь дешевле. Дальше скорость даёт
не «отключить лишнее» (лишнего почти нет), а **искать реже**: проба достижимости 5 ближайших деревьев на каждое решение
(`MindSkills.reachableTrunks`, кэш 10 с), повторные поиски мобов. Точный кэш (ключ — клетка старта, цель и изменения
блоков в области поиска) игру не меняет, но в этом прототипе не сделан. Ограничение дальности поиска мобов меняет
игру — не делал. В wood ещё 8 % времени — `LongHashMap.getValueByKey` в какой-то другой карте (не карте чанков
провайдера, её `FastLongMap` занимает те же 8 %); не разобрал, чья.

Что не получилось или сделано не так, как задумано:

- **«Без сети»** — протокол оставлен TCP на localhost, иначе `train.py` и клиент пришлось бы менять. Цена — 2–4 мс на
  запрос и меньше 1 % процессора сервера. Порт Minecraft открыт (`--port 0`), им никто не пользуется (0 % в профиле).
- **«Без диска»** — мир каждой арены копируется с диска при старте (около 16 МБ). Своего `ISaveHandler` в памяти нет:
  после первого сброса сохранение и так выключено, профиль — 0 %.
- **Свой безголовый харнесс без FML** не делал: мод живёт на событиях FML. Арены — полноценные серверы Forge в своих
  загрузчиках, это проще и сохраняет игру как есть.
- **Арены не делят классы**: каждая грузит Minecraft, Forge и мод заново (около 0.5 ГБ на арену, около 10 с на старт).
  Общий загрузчик с несколькими мирами потребовал бы переписать десятки статических полей мода.
- **Лок-шаг `train.py`** (все среды ждут самую медленную) съедает часть выигрыша от многих арен. Асинхронный сбор
  (каждая арена — свой поток, батч из готовых) — следующий шаг для обучения на движке.
- **Замеры на общем ПК.** Ночью ПК уснул посреди цепочки прогонов (01:02–11:18), часть замеров пришлось повторить;
  рядом временами шёл чужой рендер. Поэтому сравнение «один к одному» — парное, одновременно.
- Первая версия очереди прогонов запустила следующие шаги раньше времени, и они наложились на матрицу (порты заняты,
  x8 и x14 в `bench-matrix.jsonl` неполные). Итоговые цифры взяты из повторов: `bench-final.jsonl`, `bench-pair.jsonl`.
- `waves:normal`: сеть в настоящей игре не проходит ни одного эпизода (0 из 13–130 во всех прогонах; в симуляторе —
  0.87). Это самый большой разрыв симулятор ↔ игра из увиденных. Здесь он только измерен, не разбирался.

**Рекомендация.** Движок как среда — рабочий и честный (та же игра: пути совпадают точка в точку, исходы — в пределах
шума), быстрее нынешних серверов в 1.8–2 раза и экономнее по памяти, но медленнее Python-симулятора в 26–180 раз.
Поэтому не «вместо», а «вместе»:

1. Основной объём обучения — на симуляторе.
2. Каждые N эпох — проверка и дообучение на движке (12–14 арен на этом ПК — 30–90 решений/с).
3. Главное, что даёт движок, — **аудит «маска ⇔ исполнимость» на настоящей игре** (раздел 8). Он нашёл ошибки, из-за
   которых сеть в игре сыпала сотнями невыполнимых действий; часть исправлена, остальное (`ascend:surface`,
   `mine:iron_ore`, пути домой) — следующие цели.
4. После правок масок короткое дообучение на движке (25 мин) не ухудшило сеть в игре, в отличие от `v31real2`: 37/40
   против 32/40 у `v31-sim-epoch-472` на 10 эпизодах на сценарий. Это ориентир. Прежде чем ставить веса в мод, нужна
   большая проверка.

## 8. Маска ⇔ исполнимость

В дублях 9–10 ноября большая часть решений сети — петли провалов: маска разрешает, навык не может (`place_at …
NO_ITEMS` сотнями, `repair_wall/build_wall BLOCKED`, `NOT_VISIBLE` у верстака под землёй). Движок проверяет это на
настоящей игре.

**Аудит.** `RlEnv.ended` для каждого решения, которое маска разрешила, записывает исход навыка: код результата, а провал
за первую игровую секунду — с пометкой `@0` (навык даже не начал работу). Команда протокола `{"op":"audit"}` отдаёт
сводку (`"reset": true` — очистить). `tools/rl/engine_audit.py` гоняет сценарии на аренах движка и суммирует:

    python tools/rl/engine_audit.py --n 2 --seconds 40 --policy random --out build/rl/engine/audit-after-random.json

Политика `random` — равномерно по разрешённым действиям, кроме `noop`: так проверяется сама маска, а не привычки сети.

Что нашлось и что исправлено:

1. **`place:block@… → NO_ITEMS` на старте** — ошибка навыка, а не маски. `PrimSkills.place` брал предмет по названию
   материала с мета 0 (`log` → дуб), а `Body.stack` ищет точное мета: у агента с берёзовыми брёвнами или еловыми
   досками маска «блок есть» верна, навык отказывал мгновенно. Теперь блок берётся из настоящей стопки сумки
   (`PrimSkills.blockStack`, её мета).
2. **`place:block@front/hole/… → BLOCKED` на старте** — клетка свободна, но приставить блок не к чему. Факт
   `tgt_<цель>_free` (он и в наблюдении) теперь значит «блок сюда встанет»: клетка берёт блок и есть твёрдая грань рядом
   (`Skills.supports`); у `below` — место над головой (см. 4).
3. **`place:block@left/right/… → GONE`** (дубли v3.1: 86) — маска и `PrimSkills.free` считали свободной текущую
   жидкость, `RlNear` — любой нетвёрдый блок (факел, рельс), а `Body.place` принимал только «мягкую» клетку. Теперь
   `Body.place` ставит и в текущую жидкость (как игрок), а `nb_<d>_free` дополнительно сверяется с настоящей клеткой.
4. **`place:block@below`** стоя невыполним: в клетке собственное тело (`clearCell` → `BUSY`). Игрок ставит блок под
   себя прыжком — теперь это делает `pillar` (тот же навык, что `pillar:up`), а маска требует места над головой. Это
   последнее условие добавлено после аудита «после» (в таблице его ещё нет); по аудиту под обучением — раздел 6.
5. **`dig@front_down → NOT_VISIBLE`** (42 % разрешённых): блок перед собой на уровень ниже не виден, если перед собой
   на уровне ног твёрдый блок. Правило `nb_front_down_dig` в `RlNear.java` и `sim_near.py` одинаково (симулятор тоже
   больше не разрешает невидимое), тесты `RlTest.near` и `test_rl_sim31.py`.
6. **`place:crafting_table/furnace/chest → NOT_VISIBLE` под землёй** (дубль: 347 подряд): `place_spot`
   (`MindSkills.beside`) искал мягкую клетку на твёрдом в радиусе 2 — в туннеле это может быть клетка за стеной. Теперь
   нужна и грань опоры, видимая глазами агента в досягаемости (`Body.seesFace`, та же проверка, что в `Body.place`);
   та же клетка берётся и навыком.
7. **`build_wall/repair_wall → BLOCKED/OUT_OF_REACH`** (дубль: 238 и 316): факт маски `wall_blocks` теперь ненулевой,
   только если из первых 6 клеток, которые взял бы навык (снизу вверх, ближайшие), хоть одна принимает блок и у
   `PlaceFrom` есть план — место, куда агент дойдёт и откуда увидит грань (`DefenseSkills.canPut`).
8. **`light_area → OUT_OF_REACH`** (35–38 %): то же для `light_spots` (факт только маски) — сделано после аудита «после»,
   цифр по нему в таблице нет.

Правила-данные в `rl/actions.json` не менялись (хеши действий 3 и 3.1 те же): исправлены навыки и **факты**, из которых
правила считаются (`slot_block`, `tgt_*_free`, `nb_*_free`, `nb_front_down_dig`, `place_spot`, `wall_blocks`,
`light_spots`). Поэтому Java = Python по правилам остаётся (`test_rl_spec2.py`), веса v3.1 подходят без переделки, а
маска в обычной игре (`PolicyMind` берёт те же `RlEnv.facts`) исправлена вместе со средой. Из перечисленных фактов в
наблюдение входит только `tgt_*_free` — его смысл стал строже.

Что осталось (после правок, решения, провалившиеся на старте): `retreat:home`/`go_to:base`/`ascend:surface` →
`NO_PATH@0` (маска не знает, есть ли путь; проверка стоила бы поиска пути на решение), `place:block@front_down`
`NOT_VISIBLE@0` (15 %), `dig@<сторона>` → `NO_SPOT@0` (4–6 %), `descend:mine` → `NO_TOOL` (27 %). Память срубленных
деревьев (`chop_tree:near` к пустому месту, задача #1053) в этом прототипе не трогал: она одинакова на сервере и
в движке.

## 9. Ветка rl/fixes: память деревьев, пути из-под земли, руда, волны, v32

**#1053, память срубленных деревьев.** Стволы, которые экипаж помнит рядом, при каждом поиске стволов пересматриваются
глазами агента (в радиусе 10, а при входе в новый чанк — всё, что в поле зрения): чистый луч через старое место — бревна

фантомных деревьев нет (рубка убирает дерево из мира), так что правила совпадают.

**Пути из-под земли.** `ascend:surface` без пути к своей лестнице (яма, столб, пещера: `NO_PATH` у 85 % разрешённых)

## 10. Скорость сбора: асинхронность, кэш путей, губернатор

**Асинхронный сбор** (`train.py --async`, по умолчанию включён для движка и серверов). В синхронном режиме каждая
арена ждала самый медленный шаг раунда: навык длится от 1 до 60 игровых секунд. Теперь воркер получает следующие
действия, как только вернулся его собственный шаг. Решение принимает политика в том виде, в каком она есть в момент
наблюдения: шаг, висящий во время обновления, отстаёт на одно обновление (это покрывает отношение вероятностей PPO).
Замер: 8 арен, v31eng1 зафиксирована (`--lr 0`), wood/pickaxe/iron/farm/waves:normal поровну, по 6 минут:

| | решений/с | эпизодов/мин | успех |
|---|---|---|---|
| синхронно | 18.7 | 17.2 | 0.796 |
| асинхронно | 46.0 (×2.5) | 38.7 | 0.795 |

Асинхронный прогон шёл, пока губернатор (ниже) держал на стоянке до 3 из 8 арен: другие программы брали 30–50 % CPU.

**Точный кэш путей** (`FastPath.Cache`, выключается `-Daiguide.rl.engine.pathcache=false`). Поиск, заданный снова с
теми же входами, возвращает те же точки, если ни один блок не изменился в чанках, которые поиск мог прочитать
(конец ± дальность + 3, старт ± 3). Входы: клетки старта и конца, размер, дальность, флаги дверей и воды, допустимое
падение (зависит от цели и здоровья моба), собственная клетка сущности (правило рельсов), лава. Об изменении блоков мир
сообщает слушателям (`IWorldAccess`), но только в чанке, где `isPopulated`. У чанков арены это никогда не так: их флаги
«тикнут» и «свет заполнен» ставит только тик игрока. Поэтому кэш ставит эти флаги на чанках сохранённого поиска,
когда их украшение закончено (сам чанк и соседи по −x/−z). Без игроков флаги ни на что больше не влияют: от них
зависят пакеты игрокам и правка света на краю чанка при тике игрока. Новый загруженный чанк (флаги сброшены) кэш не
доверяет; восстановление арены (целые чанки пишутся мимо уведомлений) очищает кэш. Проверка
`-Daiguide.rl.engine.check=1` — каждый поиск дублируется игровым, включая ответы из кэша.

`tools/rl/engine_pathcache.py`, 4 арены, wood/iron/waves:normal по 120 с, v31eng1:

| | wood, игр. с/с | iron | waves:normal | поисков | из кэша | расхождений |
|---|---|---|---|---|---|---|
| проверка (каждый поиск ×2) | 298 | 424 | 97 | 134 511 | 42 166 | **0** |

**Губернатор ресурсов** (`tools/rl/governor.py`; `train.py` включает его сам, `--no-governor` выключает; обёртка для
любой команды — `python tools/rl/governor.py run -- <команда>`; разовый взгляд — `governor.py once`). Каждые 2 с он
смотрит загрузку чужих программ: весь CPU минус дерево наших процессов по CPU-секундам, свободную память, GPU во время
сбора, запущен ли League of Legends. Решения:

- **League:** Idle, 1 поток torch и 1 арена, обновление спит между мини-батчами (четверть GPU);
- **иначе:** BelowNormal, потоки и арены по свободным ядрам (сглажено) с запасом 2 ядра;
- **сжатие** (арен вдвое меньше, 1 поток): чужие программы прибавили 25 пунктов, держат больше 70 %, свободной
  памяти меньше 4 ГБ или GPU занят чужими;
- **пауза:** больше 90 % или памяти меньше 2 ГБ. Дочерние процессы приостанавливаются (`NtSuspendProcess` —
  все потоки), запуск ждёт. Снимается после 5 спокойных замеров.

Каждое изменение — строка `<run>/governor.jsonl`: замер, решение, причина. Аварийное завершение не оставляет
приостановленных детей и JVM (atexit). Тест — `tools/tests/test_governor.py`: правила и настоящая приостановка с
возобновлением.
